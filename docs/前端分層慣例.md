# 前端分層慣例

這份文件定義這個專案前端的**分層與判準**：誰負責碰 `$fetch`、token 存哪、
錯誤在哪一層決定要不要跳 toast。頁面不該知道這些事。

**先講一個常見的陷阱**：很多 Nuxt 專案的 HTTP 封裝是為了 Java/Spring 生態那種
「HTTP 一律 2xx、靠 body 的 `code` 判斷成敗」的回應約定寫的。這個後端的約定
完全相反，那種寫法搬過來會壞（見下方「兩種回應約定」）。

> 定稿 2026-09-05（Ch13）。

---

## 1. 分層與職責

```
app/api/*.ts                    逐 domain 的薄封裝，一個檔案一個資源
app/composables/useMyService.ts 統一的 HTTP 封裝（唯一碰 $fetch 的地方）
app/model/api/schema.d.ts       ← openapi-typescript 產的，不手寫、不手改
app/utils/auth.ts               token 存取（useCookie）
app/middleware/auth.global.ts   全域路由守衛，publicPages 白名單
app/stores/*.ts                 Pinia，只放跨頁面的狀態（目前只需要 auth 與 notification）
app/pages/*.vue                 頁面，只組合上面這些，不直接呼叫 $fetch
```

**這個分層在解決什麼**：頁面不該知道 token 存在哪、錯誤怎麼顯示、baseURL 是什麼。
`api/*.ts` 讓頁面看到的是 `surveys.findAll({ page: 1 })` 而不是一個網址字串；
`useMyService` 讓「錯誤要不要跳 toast」只有一個地方決定。

**`api/*.ts` 的形狀**：

```ts
import { useMyService } from '~/composables/useMyService'
import type { HttpOption } from '~/composables/useMyService'
import type { components, paths } from '~/model/api/schema'

type Survey = components['schemas']['SurveyEntity']
type Paginated = components['schemas']['PaginatedSurveysEntity']
type ListQuery = NonNullable<paths['/surveys']['get']['parameters']['query']>

export const surveys = {
  findAll: (query: ListQuery, option?: HttpOption<Paginated>) =>
    useMyService.fetch<ListQuery, Paginated>('surveys', query, option),

  findOne: (id: string, option?: HttpOption<Survey>) =>
    useMyService.fetch<never, Survey>(`surveys/${id}`, undefined, option),
}
```

**型別一律從 `schema.d.ts` 取**，不要另外手寫 `~/model/api/<resource>.ts` 這種
`IFindAllXxxReq / IFindAllXxxResp`。手寫的型別會跟後端漂移而沒有人知道；產的不會。

## 2. `useMyService` —— 唯一碰 `$fetch` 的地方

### 兩種回應約定

Java/Spring 生態常見的 `ApiResponse<T>` 約定，跟這個後端的約定是相反的：

| | `ApiResponse<T>` 那種約定 | **這個專案的後端**（Ch6 定的） |
| --- | --- | --- |
| 業務錯誤的 HTTP 狀態 | **一律 2xx** | **真實狀態碼**（400/401/403/404/409/500） |
| 怎麼判斷失敗 | body 的 `code !== 0` | HTTP 狀態碼非 2xx |
| 錯誤內容 | `{ code, message, data }` 攤在最外層 | `{ error: { code, message, fields? } }` **包了一層** |
| token 續期 | 每個回應回一個續期 header | **沒有**，一小時過期就得重新登入 |
| token 怎麼帶 | 自訂 header | `Authorization: Bearer <token>` |

所以 `ok` 的計算、錯誤 toast 的觸發點、`error.message` 的取法都要**依這個後端**設計。
拿前一種約定的封裝來用，後果是 `onResponse` 裡那段 `if ('code' in res && res.code !== 0) throw res`
在這個後端**永遠不會觸發**（成功的回應裡根本沒有 `code` 這個 key），
於是所有錯誤都只能靠 `onResponseError` 撿 —— 剛好還能動，但邏輯是死的，
下一個人讀到會以為它有在做事。

### 三個跟後端無關的判斷

1. **`ok` 用 `hadError` flag，不要用 `!error.value`。**
   `throw undefined` 這種 falsy 例外會讓 `!undefined === true`，變成 false-success。
   ```ts
   let hadError = false
   try { ... } catch { hadError = true; ... } finally { ok.value = !hadError }
   ```
2. **錯誤 toast 只有一個來源。** 封裝層跳過了，呼叫端在 `if (!ok.value)` 分支就不要再跳。
   給一個 `silent?: boolean` 讓批次操作可以自己彙整。
3. **in-flight 期間 `ok` 先設 false**，refresh 完成才反映真正結果。

### 這個專案的骨架

```ts
export type HttpOption<T> = Omit<NitroFetchOptions<string>, 'baseURL' | 'timeout'> & {
  responseType?: 'json' | 'text'   // blob 這個專案用不到，別留
  silent?: boolean
}

export interface MyFetchResult<T> {
  data: Ref<T | null>
  pending: Ref<boolean>
  error: Ref<ApiError | null>     // ← 攤平後的 { code, message, fields? }
  ok: Ref<boolean>
  refresh: () => Promise<void>
}
```

`useMyFetch` 內部依序做四件事：

1. **`onRequest`** —— 從 cookie 取 token，有就設 `Authorization: Bearer <token>`。
   （不用 `credentials: 'include'`：token 走 header 不走 cookie，
   後端的 CORS 因此可以不必開 credentials —— 那是 Ch14 要決定的事。）
2. **`onResponseError`** —— 錯誤形狀在這裡攤平。
   後端的錯誤 body 是 `{ error: { code, message, fields? } }`，要先攤平：
   ```ts
   // ⚠️ ApiError 的型別要**從 schema.d.ts 取**，不要手寫 interface ——
   // 後端改了錯誤形狀時，手寫的那份不會讓 typecheck 紅（Ch15 實際發生過）。
   const body = response._data as { error?: ApiError }
   const apiError: ApiError = body?.error ?? { code: 'INTERNAL_ERROR', message: '發生未知錯誤' }
   ```
   **fallback 不能省**：CORS 被擋、gateway 回 HTML 錯誤頁、後端沒起來，
   這三種情況 `response._data` 都不是預期的形狀。
3. **依 `code` 分支，不要解析 `message`。** `message` 的內容會隨版本變動，
   `code` 是契約的一部分（產出來的型別是字面值聯集，打錯字編譯不過）。
   - `UNAUTHORIZED` → 清 token、導 `/login`、toast「登入逾時，請重新登入」
   - `FORBIDDEN` → toast「權限不足」。**不要試圖分辨是角色不足還是不是你的資源**，後端刻意讓兩者對外一樣
   - 其他 → toast `message`（顯示可以用 message，**分支不行**）
4. **`ok = !hadError`**（見上）。

`useMyService` 對外只需要 `fetch / post / patch / remove` 四個。
不要預先加 `put / uploadFile / postFormData` —— 這個後端沒有 PUT、沒有檔案上傳。

### 對照組：一個常見的失敗模式

封裝跟後端契約脫鉤時，典型的症狀長這樣：呼叫端用 `error.value?.msgs?.length`
判斷失敗，但後端根本不回 `msgs` 這個欄位 —— 於是那個判斷**永遠是 undefined**，
錯誤被靜默跳過，使用者看到「成功」。手寫型別的專案只能靠 eslint 的
`no-restricted-syntax` 之類的規則去擋。

**這個專案有結構性的解法**：
型別是從 `/docs-json` 產的，寫一個後端不存在的欄位**當場編譯不過**，
不需要 eslint 規則去擋。這就是 Ch13 那句「型別品質 = entity 標記品質」的另一面。

## 3. token 存取：全專案只能有一個 cookie ref

⚠️ **這一節在 Ch14 輪 ③ 被實測改寫過。原本的範例（每個函式各呼叫一次 `useCookie`）
會產生一個只在瀏覽器裡出現的 bug。**

### 那個 bug

登入成功之後 `GET /auth/me` 回 401「缺少存取權杖」—— 看起來像登入壞了，
其實是**同一個 tick 內的競態**：

```
setToken(token)   → ref A.value = token，watch 排進 microtask，document.cookie 還沒變
fetchMe()         → 又呼叫一次 useCookie → 新的 ref B → 讀 document.cookie → null
                  → 不帶 Authorization → 401
```

根因在 Nuxt 的實作（`node_modules/nuxt/dist/app/composables/cookie.js`）：

```js
const cookies = readRawCookies(opts)        // 每次呼叫都重讀 document.cookie
const cookie = ref(cookies[name])           // 每次呼叫都是一個新的 ref
if (opts.watch) watch(cookie, () => writeClientCookie(...))   // 寫入靠 watch → 非同步
```

**SSR 測試抓不到它**（SSR 走的是 `cookieServerRef`，行為不同），
後端的 e2e 更碰不到 —— 它只在瀏覽器裡存在。

### 對策是結構性的，不是加 `nextTick`

`app/utils/auth.ts` 只匯出**一個** composable，而且明寫誰可以呼叫它：

```ts
export const TOKEN_KEY = 'survey_token'
const TOKEN_MAX_AGE = 60 * 60   // 對齊後端 token 的壽命

/** ⚠️ 全專案只有 stores/auth.ts 可以呼叫它，其餘一律用 useAuthStore().token */
export function useTokenCookie() {
  return useCookie<string | null>(TOKEN_KEY, { maxAge: TOKEN_MAX_AGE, sameSite: 'lax' })
}
```

`stores/auth.ts` 持有那唯一的 ref，其他地方（`useMyService`、守衛、頁面）一律讀 `auth.token`。
`getToken` / `setToken` / `removeToken` 三個函式**已經刪掉** —— 它們本身就是陷阱。

> 順帶：token 存 cookie 不是為了讓瀏覽器自動帶去後端（那需要 `credentials`），
> 而是為了讓 **SSR 那一側也讀得到** —— 路由守衛在伺服器端就會跑一次，
> 那裡沒有 `localStorage`。送出時仍然是前端自己讀出來放進 `Authorization` 標頭。

### 路由守衛

```ts
export default defineNuxtRouteMiddleware(async (to) => {
  const publicPages = ['/login']
  const isPublic = publicPages.includes(to.path)

  const auth = useAuthStore()
  const token = auth.token          // ← 不是 getToken()

  if (!token) return isPublic ? undefined : navigateTo('/login')

  // 有票但還不知道是誰（首次進站或 reload）→ 換回身分
  if (!auth.isLoggedIn) {
    // silent：進站時票剛好過期很正常，不必跳 toast，而且導頁要由這支守衛決定
    const ok = await auth.fetchMe({ silent: true })
    if (!ok) return isPublic ? undefined : navigateTo('/login')
  }

  if (isPublic) return navigateTo('/surveys')
})
```

⚠️ **守衛只看「有沒有票」，不看票有沒有過期。**
token 一小時過期而且不會續期，所以「有票但已失效」是常態 ——
真正把人踢出去的是 `useMyService` 收到 401 的那一刻。
兩者缺一不可：守衛擋沒登入過的人，401 擋票過期的人。

⚠️ **`silent` 在這裡有第二層意思**：它同時抑制 toast 與 `useMyService` 的自動導頁。
少了它，守衛與 `useMyService` 會兩邊搶著決定要導去哪。

## 4. Vuetify 在 Nuxt 4 的接法

`nuxt.config.ts` 四處缺一不可：

```ts
build:  { transpile: ['vuetify'] },
css: [
  'vuetify/lib/styles/main.sass',
  '@mdi/font/css/materialdesignicons.css',
  '~/assets/scss/main.scss',
],
vite: {
  ssr: { noExternal: ['vuetify'] },
  // .ts 要排在 .js 前面：曾經因為誤 emit 的 .js 蓋過同名 .ts，
  // ~/utils/auth 解析到 CommonJS 版本
  resolve: { extensions: ['.mjs', '.mts', '.ts', '.tsx', '.js', '.jsx', '.json'] },
},
```

再加一支 `plugins/vuetify.ts` 做 `createVuetify()` 並 `nuxtApp.vueApp.use(vuetify)`。

## 5. 已經決定的兩件事（Ch14）

- **不改用 `openapi-fetch`。** 它能直接吃 `paths` 型別、省掉 `api/*.ts` 的手寫泛型，
  但代價是換掉整個 `useMyService` 的形狀，而 §2 那三個「跟後端無關的判斷」得自己重接。
  **維持照這份分層手寫** —— 那三個判斷是踩出來的，比省幾行泛型值錢。
- **CORS 不開 credentials。** `credentials` 管的是「瀏覽器要不要**自動**帶上 cookie」，
  而這裡的 token 是前端自己讀出來放進 `Authorization` 標頭的 —— 瀏覽器全程不必自動帶任何東西。
  開了只是擴大攻擊面（而且 `origin` 就不能用 `*`）。後端 Ch14 輪 ① 照這個決定設定。
